# User Dashboard — Design Spec

**Date:** 2026-05-24
**Subsystem:** A (of A → B → C → D roadmap)
**Status:** Approved

---

## Scope

Personal dashboard for every logged-in user: recent Paperless documents, Signal notification log, and preference toggles. Admin users additionally keep access to `/users` (user management).

Out of scope for this spec: mail integration (B), Signal two-way/tickets (C), role-based permissions (D).

---

## Architecture

```
Browser
  → Traefik (forward auth via Authentik)
  → Portal /dashboard (Next.js server component)
        reads X-authentik-uid + X-authentik-username from request headers
        forwards X-Internal-Secret + X-Authentik-Uid to internal API
  → NestJS API :3001 (internal Docker network only)
        ├─ GET  /users/me/documents      → Paperless API
        ├─ GET  /users/me/notifications  → doc_notifications table
        ├─ GET  /users/me/preferences    → Authentik attributes
        └─ PATCH /users/me/preferences  → Authentik attributes
```

### Identity & security

- **`X-authentik-uid`** (numeric Authentik pk) is the user identifier — forwarded by Traefik, read by portal, sent to API.
- **`X-Internal-Secret`** — shared 64-char random token in `.env` (`INTERNAL_API_SECRET`). Required on all `/users/me/*` requests. The NestJS guard rejects any call without the correct secret, even from within the Docker network. Generated by `install.sh` alongside existing secrets.
- The combination of both headers means: only the portal (which Authentik already verified) can call these endpoints.

## Backend

### New module: `UsersMeModule`

New file group alongside existing modules:

```
api/src/users-me/
  users-me.module.ts
  users-me.controller.ts   — /users/me/* endpoints
  users-me.service.ts      — business logic
```

### Guard: `InternalSecretGuard`

Applied to all `/users/me/*` routes. Reads `X-Internal-Secret` from the request header and compares to `INTERNAL_API_SECRET` env var. Returns 403 on mismatch.

### Endpoints

| Method | Path | Response |
|---|---|---|
| `GET` | `/users/me/documents` | `{ docs: PaperlessDoc[] }` — last 10, filtered by owner username |
| `GET` | `/users/me/notifications` | `{ notifications: DocNotification[] }` — last 20 for user's phones |
| `GET` | `/users/me/preferences` | `{ signal_doc_notify: boolean, signal_digest_mode: boolean }` |
| `PATCH` | `/users/me/preferences` | Same shape — writes to Authentik attributes |

### Identity resolution

`UsersMeService` accepts the Authentik uid from the header. It calls `GET /api/v3/core/users/{uid}/` once to get `username` and `attributes.phone`/`attributes.phone2`. These are used to:
- Filter Paperless docs by `owner` field
- Filter `doc_notifications` by `phone` column

The service resolves uid → user info with a single Authentik call per request.

### Preferences

Stored as string attributes on the Authentik user object:
- `signal_doc_notify`: `"true"` (default) | `"false"`
- `signal_digest_mode`: `"true"` | `"false"` (default) — toggle wordt opgeslagen maar heeft pas effect in subsysteem B

PATCH merges into existing attributes — preserves `phone`, `phone2`, and any other fields.

### Effect on DocumentsService

`onConsumed()` reads `signal_doc_notify` from Authentik attributes for the document owner before sending the Signal prompt. If `"false"`, skips Signal entirely (doc is still saved to DB).

## Frontend

### New route: `portal/app/dashboard/page.tsx`

Server component. Reads `X-authentik-uid` and `X-authentik-username` from incoming request headers. Makes three parallel fetch calls to `INTERNAL_API_URL` with `X-Internal-Secret` and `X-Authentik-Uid` headers.

**Page layout:**

```
┌─────────────────────────────────────┐
│  [Avatar initial]  Welkom, Jan      │
├─────────────────────────────────────┤
│  📄 Recente documenten              │
│  ┌──────────────────────────────┐   │
│  │  Doc titel          14 mei   │   │
│  │  Doc titel          12 mei   │   │
│  └──────────────────────────────┘   │
├─────────────────────────────────────┤
│  🔔 Notificatie log                 │
│  ┌──────────────────────────────┐   │
│  │  ✅ Samenvatting verzonden   │   │
│  │  📄 Prompt verstuurd         │   │
│  └──────────────────────────────┘   │
├─────────────────────────────────────┤
│  ⚙️  Instellingen                   │
│  Signal-melding bij nieuw doc  [●]  │
│  Digest-modus (dagelijks)      [○]  │
└─────────────────────────────────────┘
```

Each section is wrapped in `<Suspense>` with a skeleton fallback — sections load and render independently.

### Progressive loading

- Documents section failing (Paperless unreachable) → shows "Documenten tijdelijk niet beschikbaar" — rest of page unaffected.
- Notifications section failing → shows empty state — rest unaffected.
- Preferences failing → toggles render as disabled — no silent data loss.

### Toggle interaction

Client component wraps the toggles. On change: optimistic update (toggle flips immediately), then `PATCH /users/me/preferences` via the portal's `/api/me/preferences` route (Next.js API route proxies to internal NestJS). On error: revert with toast notification.

### Portal Next.js API routes (proxy layer)

```
portal/app/api/me/
  documents/route.ts       — proxies GET to INTERNAL_API_URL/users/me/documents
  notifications/route.ts   — proxies GET to INTERNAL_API_URL/users/me/notifications
  preferences/route.ts     — proxies GET + PATCH
```

These routes inject `X-Internal-Secret` and `X-Authentik-Uid` from the server-side session context — the browser never sees the internal secret.

### Homepage update (`portal/app/page.tsx`)

Add a "Dashboard" button in the `Dashboard` component alongside the existing "Gebruikersbeheer" link. Same card style, distinct colour (e.g. emerald vs blue) so the two are visually differentiated.

## Data types

```typescript
interface PaperlessDoc {
  id: number;
  title: string;
  created: string;       // ISO date
  document_type?: string;
}

interface DocNotification {
  id: string;
  documentId: string;
  status: 'pending' | 'processing' | 'done' | 'failed';
  createdAt: string;
  // doc title joined from doc_documents
  documentTitle?: string;
}

interface UserPreferences {
  signal_doc_notify: boolean;
  signal_digest_mode: boolean;
}
```

## What is NOT in this spec

- Mail integration (inbox, out-of-office) → subsystem B
- Signal two-way / support tickets → subsystem C
- Role-based access, audit trail → subsystem D
- Push notifications, read receipts, typing indicators → subsystem C/D
